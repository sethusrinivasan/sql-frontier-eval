1. Analytical Significance & What It Means

Scenario & Frontier Trap
Business Scenario & Problem

When assembling retrieved chunks for an LLM prompt, you have a strict token limit (e.g. 1,000 tokens). You must greedily pick highest-similarity chunks until the cumulative token sum would exceed the budget.

4. Queries Executed (Candidate vs Golden Ground Truth)

Beautified & Syntax Highlighted
Database Engine Context: This query was executed and profiled on DuckDB 2.0 In-Memory Engine with equivalent analytical syntax and execution verification on PostgreSQL 18.7 + Extensions (Docker Compose).
Candidate SQL Executed by gemini-3.8-flash-low (Runtime on 1M Rows: 98.30 ms) 
WITH ranked_chunks AS
  (SELECT chunk_id,
          token_count,
          array_cosine_similarity(vec, [1.0, 0.0]::FLOAT[2]) AS score,
          sum(token_count) OVER (
                                 ORDER BY array_cosine_similarity(vec, [1.0, 0.0]::FLOAT[2]) DESC) AS cumulative_tokens
   FROM rag_candidate_chunks)
SELECT chunk_id,
       token_count,
       cumulative_tokens,
       round(score, 4) AS similarity_score
FROM ranked_chunks
WHERE cumulative_tokens <= 1000
ORDER BY similarity_score DESC;
Golden Reference Ground Truth SQL (Runtime on 1M Rows: 111.74 ms) 
-- Greedily pack chunks ordered by similarity up to strict 1,000 token budget
 WITH ranked_chunks AS
  (SELECT chunk_id,
          token_count,
          array_cosine_similarity(vec, [1.0, 0.0]::FLOAT[2]) AS score,
          sum(token_count) OVER (
                                 ORDER BY array_cosine_similarity(vec, [1.0, 0.0]::FLOAT[2]) DESC) AS cumulative_tokens
   FROM rag_candidate_chunks)
SELECT chunk_id,
       token_count,
       cumulative_tokens,
       round(score, 4) AS similarity_score
FROM ranked_chunks
WHERE cumulative_tokens <= 1000
ORDER BY similarity_score DESC;
