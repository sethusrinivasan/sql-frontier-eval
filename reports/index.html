Query Execution Plan Analysis & Physical Indexing Architecture

Physical Profiling Deep Dive

1. Empirical Operator Bottleneck Decomposition

Across all 120 tasks and 108M+ records profiled with EXPLAIN ANALYZE, sequential table scans account for only 5.5% of execution time. Over 94.5% of runtime is consumed in-memory: Window Functions (30.0%), Hash Group-By (19.5%), Sorts (15.2%), and Projections/Joins (29.8%).

2. The Indexing Paradox: Columnar OLAP vs. Row-Store PostgreSQL

In Columnar Engines (DuckDB): Traditional secondary B-Tree / Adaptive Radix Tree (ART) indexes are completely bypassed by the optimizer during analytical aggregations and joins. DuckDB scans contiguous columnar vector chunks (2,048 tuples) using AVX2 SIMD instructions at memory bus speeds (~0.7 ms per 1M integers). Maintaining pointer-based tree indexes degrades cache locality without performance gain. The true physical optimization lever in DuckDB is Physical Ingestion Clustering (ORDER BY DDL) and Min-Max Zone Maps.

In PostgreSQL 18+: In unindexed tables, PostgreSQL falls back to row-by-row Seq Scan and explosive Nested Loop joins ($O(N^2)$), causing 10x-50x latency regressions. However, generic single-column B-Trees are insufficient for analytical workloads.

3. Why Frontier LLMs Failed to Recommend the Right Indices

A. The "SELECT-Only" Scoping Blindspot: Standard text-to-SQL prompts confine the model to emitting a SELECT query, treating schema DDL and indexing as immutable external constants without agency to optimize storage.

B. OLTP Textbook Muscle Memory: Pre-trained largely on web-app CRUD repositories (Django, Rails), LLMs reflexively advise single-column B-Tree indexes on every foreign key, unaware that analytical queries require composite covering indexes or specialized access methods.

C. Cardinality and Skew Blindness: Models generate SQL in a statistical vacuum without inspecting NDV (distinct values), sort correlations, or null fractions. Joining on non-selective keys triggered up to 250 billion Cartesian comparisons.

D. Absence of EXPLAIN Plan Feedback Loops: Models operate purely one-shot without observing operator cost percentages, row estimates vs actuals, or disk spill warnings from EXPLAIN ANALYZE.

4. What Models Could Have Done Better to Optimize the DB Setup

Composite Covering Indexes (Postgres INCLUDE): Emitting CREATE INDEX ON table (filter_col, join_col) INCLUDE (payload_cols); enables pure Index-Only Scans without touching the heap.

Specialized Physical Extensions: Recommending HNSW vector indexes (USING hnsw (embedding vector_cosine_ops)) for embeddings, GIN trigram indexes for fuzzy text search, GiST for temporal range overlaps, and BRIN for append-only timestamp streams.

Dual-Phase Agentic Architecture: Formulate database physical layout (clustering keys, partition boundaries, and indexes) before generating queries, verified through an automated EXPLAIN ANALYZE feedback loop.
